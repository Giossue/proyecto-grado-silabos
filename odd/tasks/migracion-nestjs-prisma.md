# Migración al estándar de TICs: NestJS + Prisma

Objetivo: cumplir la «Especificación del stack tecnológico para el desarrollo de sistemas informáticos internos» de la DTIC (UEB): API independiente en NestJS con Prisma y Swagger, frontend Next.js, PostgreSQL 18, almacenamiento S3 (MinIO), Keycloak y Docker con contenedores separados, sin cambiar lo que ve el usuario.
Rama: `main` (repositorio privado). Entrega: commits por etapa. Pruebas: Vitest, typecheck, lint, build y la suite E2E completa (87) al cerrar cada etapa grande.

## Specs

- S1. Pedido: «para hoy, lo haremos de una, no pasa nada, y usariamos prisma, y ahi usar NestJS» → «ok hazlo».
- S2. PDF de la DTIC (requisitos obligatorios):
  - «Framework Principal: NestJS (Versión 12 o superior). Toda la lógica de negocio del backend debe implementarse obligatoriamente como una API independiente.»
  - «ORM y Migraciones de Base de Datos: Se recomienda la utilización de Prisma ORM o TypeORM» → Prisma.
  - «Es obligatorio documentar las APIs utilizando la especificación OpenAPI conjuntamente con Swagger UI.»
  - «Frontend: Next.js (Versión 16 o superior).»
  - «Motor de Base de Datos Relacional: PostgreSQL (Versión 18 o superior).»
  - «Gestión y Almacenamiento de Archivos: SeaweedFS / MinIO» → MinIO.
  - «Autenticación y Autorización: Se empleará Keycloak.»
  - «Dockerización … esquema desacoplado y modular por contenedores e imágenes independientes (por ejemplo: un contenedor para el backend, uno para el frontend, uno para la base de datos, uno para el almacenamiento de archivos, etc.), gestionados adecuadamente mediante volúmenes persistentes.»
- S3. Decisiones (el usuario pidió la recomendación: «confirmame eso tú», «que me recomiendas?»):
  - Estructura: un repositorio pnpm con `apps/web` (Next.js), `apps/api` (NestJS, una API modular, no microservicios: el PDF pide «un contenedor para el backend») y `packages/shared` (esquemas Zod, tipos y reglas compartidas).
  - Validación: Zod con `nestjs-zod` (`createZodDto`): DTO como clases de NestJS con `ValidationPipe` y Swagger, construidos con los esquemas Zod existentes; mismos mensajes y mismos 422.
  - Ingreso: se conserva el ingreso actual (cuentas, 2FA, sesiones) dentro de la API y se agrega el ingreso institucional con Keycloak (realm `SAC`, credenciales en `temp/keycloack.md`, fuera de git; redirección registrada `http://localhost:8000/auth/callback`, por eso la API escucha en el puerto 8000). Las credenciales de Keycloak no dan acceso a datos (probado: «Client not enabled to retrieve service account»).
  - Infraestructura: «Sí, los dos (Recomendado)»: PostgreSQL 18 y MinIO; los archivos actuales se migran a MinIO.
- S4. Contrato: la API conserva rutas (`/api/v1/...`), métodos, cuerpos, códigos (401, 403, 409, 422 con errores por campo), cabeceras (`X-RateLimit-*`) y textos; el frontend no cambia su comportamiento. Las instantáneas firmadas, sus SHA-256 y el Word siguen idénticos.
- S5. Pendientes de TICs (no bloquean): SIANET, endpoint de firma .p12, repositorio «Plantilla UEB», UEB Design System (token de GitHub Packages en `temp/keycloack.md`; va en `.npmrc` con variable de entorno, nunca en el repositorio).
