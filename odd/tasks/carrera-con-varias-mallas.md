## Specs

- S1 User: «hay que manejar de mejor manera la doble malla, ya no hay que tomarlo como una carrera aparte». New table `mallas` (Spanish names): `malla_id`, `carrera_id`, `nombre_malla`, `resolucion_malla` (optional), `numero_ciclos`, `estado_malla` (`vigente` | `en_transicion` | `cerrada`), optional start period; at most one `vigente` malla per career.
- S2 Subjects belong to a malla: `asignaturas.malla_id` NOT NULL. Design decision (parent, 2026-11-26): `asignaturas.carrera_id` stays as a denormalized copy, enforced by a composite FK `(malla_id, carrera_id) → mallas(malla_id, carrera_id)`, so career-scoped queries keep working. Subject code unique per malla (replaces unique (carrera_id, codigo_asignatura)). `numero_ciclos` moves from `carreras` to `mallas`. Creating a career creates its first `vigente` malla with the cycles given in the career form.
- S3 Curriculum screens (admin and coordination) address the malla by its own id (today `curriculumId === career.id`, `structure.ts:185`); the malla page lets the user pick the malla; the Excel curriculum import loads into the chosen malla.
- S4 Periods and syllabi: syllabus generation, scheduled subjects, subject profiles (proyecto de carrera) and readiness checks use the subjects of every non-closed malla of the career; the syllabus shows which malla it belongs to.
- S5 Data migration (generic, safe for the server): every existing career gets one `vigente` malla named «Malla <codigo_carrera>» with its cycles and subjects. The SW-8/SW-9 merge is NOT in the migration: it is a reusable script `apps/api/scripts/fusionar-carreras.sql` (psql variables keep/absorb codes) run only on `silabos_ueb_mallas`. Merge details: every existing career gets one malla with its cycles and subjects. User (2026-11-26) on the duplicated career: «Ponle cualquiera, es una bd de prueba» → `SW-8` and `SW-9` merge into career `SW-9` with two mallas: SW-8's subjects become the `en_transicion` malla, SW-9's the `vigente` one; SW-8's convocatorias, role assignments, support documents and syllabi move to SW-9.
- S6 Out of scope. User: «Pero y eso que tiene que ver con el sistema de silabos???» → no homologation table between mallas.
- S7 Migrations are written in `apps/api/prisma/migrations`; applied only to `silabos_ueb_mallas` (rehearsed first on a scratch copy). User: «puedes crear un three no?» → work in a git worktree with its own database.

- S8 API contract (shared by writers). Admin `admin/careers/:career/academic/...` and coordination `coordination/academic/...` gain:
  - `GET mallas` → `{ mallas: [{ id, name, resolution, cycle_count, state, subject_count }] }` ordered vigente, en_transicion, cerrada.
  - `POST mallas` `{ name, resolution?, cycle_count, state }`; `PATCH mallas/:malla` `{ name?, resolution?, state? }` (making one `vigente` turns the previous `vigente` into `en_transicion`; a malla with an open period's syllabi cannot be closed — Spanish validation message).
  - Existing `curriculum/:curriculum` routes keep their shape but `:curriculum` is a malla id of that career (404 otherwise); `curriculum` payload adds `malla: { id, name, state }`; `curriculum-import` takes `malla_id`.
  - Scheduled subjects / syllabus payloads add `malla_name` per subject.
